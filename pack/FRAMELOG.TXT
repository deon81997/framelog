FRAMELOG 0.1 - frame-time logger for DOS games over serial
==========================================================

WHAT IT DOES
  FRAMELOG.EXE is a small resident program for the game PC. It notices
  every page flip of a running game (writes to the VGA CRTC start address,
  or VESA display-start calls)
  and sends a timestamp per frame over a serial port to a second PC (the
  host). The host saves the frames to a CSV file and makes stats and
  graphs (average fps, 1% / 0.1% lows, frame-time plot). No overlay, no
  game patching, no files are changed. Load it once, every game is logged.

INSTALL (GAME PC)
  1. Copy FRAMELOG.EXE to the game PC, e.g. C:\FRAMELOG.
  2. Add a line to AUTOEXEC.BAT (or the game's batch file):
       C:\FRAMELOG\FRAMELOG /COM:1
     It must come AFTER  HDPMI32I.EXE -r -x , or, when NUKED SB-EMU is
     used, after the SC55 line (FRAMELOG needs HDPMI32i to be resident).
  3. Reboot. FRAMELOG prints its UART, baud rate and CPU MHz when loaded.

OPTIONS
  FRAMELOG /COM:n[,baud]    COM1-COM4 (default COM1,115200)
  FRAMELOG /COM:hex[,baud]  UART at a hex port address, e.g. /COM:2F8
  FRAMELOG /AUTO            start logging at once (no host S byte needed)
  FRAMELOG /3DA[:ms]        frames = retrace waits, for games that copy
                            to the screen (see WHICH GAMES; costs CPU)
  FRAMELOG /NOVESA          do not watch VESA page flips (INT 10h is
                            then left alone; see VESA below)
  FRAMELOG /NOMETA          send no run info (see RUN INFO below)
  FRAMELOG /NOGLIDE         do not watch DOS Glide games (INT 21h is
                            then left alone; see DOS GLIDE below)
  FRAMELOG /STATUS          counters of the loaded copy (flips, frames,
                            lost, bytes sent, host bytes, starts, traps,
                            VESA display-start calls, run info blocks
                            sent, mode sets seen)

CABLE
  Use a NULL-MODEM serial cable (crossed TX/RX) between the game PC's COM
  port and the host's COM port or USB-serial adapter. A straight cable
  does not work. 115200 baud is fine for any frame rate up to ~1200 fps.

HOST PC (Windows or Linux)
  1. Install Python 3, then:  pip install pyserial matplotlib
  2. In the HOST folder:
       py fllog.py COM3 -o run.csv --label NAME
     (or LOG.BAT COM3 run.csv NAME; on Linux python3 and /dev/ttyUSB0)
     Start it before or while the game runs. Once the game PC answers
     it prints "header", then (test9) one status line, redrawn every
     second: frames so far, fps now / average, last and slowest frame
     time, lost frames (--no-live turns it off).
  3. Play / run the demo. Press Ctrl+C on the host when done.
  4. Stats and graph, one or more runs (several = comparison):
       py flstats.py a.csv b.csv --png g.png

VESA (SVGA) GAMES
  On by default. A VESA page flip is a frame too, both ways games do it:
  - INT 10h AX=4F07h (set display start), and
  - the VBE 2.0 protected-mode interface (INT 10h AX=4F0Ah): FRAMELOG
    hands the game a copy of the card's table whose SetDisplayStart entry
    first notes the time, then runs the card's own code. Duke Nukem 3D's
    VESA modes flip this way.
  FRAMELOG needs about 1.2 KB of DOS memory for this (16 bytes with
  /NOVESA). Use /NOVESA if a VESA game or VESA driver (UNIVBE, SOLVBE)
  misbehaves with FRAMELOG loaded, and report it.

DOS GLIDE (3DFX) GAMES
  On by default. DOS Glide games load 3dfx's GLIDE2X.OVL; while the game
  reads that file, FRAMELOG patches grBufferSwap in memory so that every
  buffer swap is a frame (the file on disk is not changed).
  Start order, from the game's batch file or by hand:
       C:\HDPMI\HDPMI32I.EXE -r -x
       C:\FRAMELOG\FRAMELOG /COM:1      (or the SC55 line, then FRAMELOG)
       the game (e.g. Extreme Assault: 3DFX.BAT)
  HDPMI32i DLL-start fix: the 3dfx OVLs' start code expects DOS/4GW and
  stops with "Run-time library initialization failure: DLL load
  aborted" under HDPMI32i, with or without FRAMELOG. FRAMELOG patches
  that start code too, at load time only (/STATUS: "DLL start fixes").
  So with /NOGLIDE, or without FRAMELOG, such a game still aborts under
  HDPMI32i - run it without HDPMI32i (its own DOS4GW) then.
  Not covered yet: games with Glide built into the EXE (no GLIDE2X.OVL,
  e.g. Carmageddon's CARM3DFX): they run normally but log no frames.
  Tested only with Voodoo Graphics (Voodoo 1) OVLs 2.31 and 2.42 in
  86Box; a Voodoo2 OVL is untested.
  FRAMELOG /STATUS shows "Glide hook on: GLIDE2X.OVL opens, patched
  loads, grBufferSwap calls ..." - swaps should equal frames logged.

RUN INFO (METADATA)
  On by default. When logging starts, FRAMELOG sends the host a short
  text block (an 'M' record) right after the header, and fllog.py writes
  it into the CSV as  # gpu=...  lines, filling what you did not type:
  - gpu    the VESA BIOS name of the card (OEM string, plus vendor and
           product names on VBE 2.0+ cards); "VGA" without a VESA BIOS
  - driver VBE version and the card's OEM software revision
  - res, depth  the screen mode when logging starts (VESA modes from the
           card's mode list; VGA modes from the BIOS; mode 13h and Mode X
           read from the VGA registers, e.g. 320x240); mode = VESA 101h,
           13h, X (unchained 256 colours), text 03h ...
  - cpu    the CPU's name (CPUID brand string) or vendor + family /
           model / stepping, plus the MHz FRAMELOG measured
  If the game sets a new mode while logging (INT 10h AH=00h or VESA
  4F02h), a fresh block goes out before the next frame, and the CSV gets
  a  # change@N=res=640x480 ...  line before frame N.
  The VESA and CPU questions are asked once, when FRAMELOG loads; nothing
  is sent per frame. What you give fllog.py (--gpu, --res, a suite file)
  wins; a different game-PC value is kept as pc_res etc. /NOVESA: the
  mode is then read from the BIOS only (standard VGA modes). /NOMETA
  sends nothing and does not watch mode sets.

LIMITS
  - Protected-mode games only for now (DOS4GW, DJGPP, PMODE/W ...).
    Real-mode games are not logged yet (/RM is planned).
  - Start and stop act at the game's NEXT page flip: the game PC reads
    the host's byte only when the game flips a page.
  - Do not use the same COM port as SBEMU /DBG or serial MIDI.

WHICH GAMES LOG (tested in 86Box, Pentium II 450)
  Default: a frame = a page flip (the game writes the VGA start address).
  /3DA: a frame = a vertical retrace the game waits for (port 3DAh).
  - Duke Nukem 3D 1.3D, ScreenMode = 0: works (default mode).
  - Rise of the Triad 1.3: works (default mode).
  - Duke ScreenMode = 1 (VESA), 640x480: works (VBE 2.0 PM interface).
  - Duke ScreenMode = 2 and Heretic 1.2: copy to the screen without
    waiting for the retrace each frame: no frames in either mode.
    (Only a capture card or a later memory-watch mode can see them.)
  - Doom: flips pages in mode Y, expected to work (not tested yet).
  - Copy-to-screen games that DO wait for the retrace: use /3DA.
  - DOS Glide (Voodoo Graphics, HDPMI32i): Extreme Assault 1.1.1 demo
    and Archimedean Dynasty demo (DOS4GW FIGHT3 solo): every swap
    logged, 0 lost; Redguard demo (RGFX.EXE): logs (18 fps cap);
    Carmageddon Splat Pack (static Glide): no frames, no crash.
  If fllog.py never prints "header", the game did not flip a page (or,
  with /3DA, wait for a retrace) yet.

MEASURED COST
  About 0.35% of the game's CPU at 70 fps on a Pentium II 450.
  VESA flips (INT 10h 4F07h, 70 fps): no measurable cost (-0.09%).
  Run info (M records, test4): no measurable cost (3 runs each, FLIP
  VESA 70 fps + MIDI: +0.07% spare CPU vs test3, noise 0.6%).
  /3DA traps every retrace-port read (3 million in 30 s for a game that
  waits for vsync): the game keeps its frame rate and SBEMU/SC-55 load is
  unchanged in tests, but its wait loops run slower - leave it off unless
  the game does not flip pages.
  DOS Glide (test8): GLFLIP 600 frames at 50 fps on Voodoo Graphics,
  hooked vs not hooked, 2 boots x 4 runs each: -0.08% and -0.06% spare
  CPU (logging included); the DLL-start fix costs nothing after load.
  SBEMU / SC-55 load is unchanged (no IRQ0, PIT or keyboard hooks).

TEST GAME
  FLIP.EXE SECONDS FPS [LONG] [M] flips the screen at a fixed rate; every
  LONG-th frame (default 10) takes twice as long. M also plays MIDI on
  MPU-401 330h. B flips with VESA INT 10h 4F07h in 640x480 (mode 101h)
  instead. Example: FLIP 20 70  (log it with fllog.py on the host).
